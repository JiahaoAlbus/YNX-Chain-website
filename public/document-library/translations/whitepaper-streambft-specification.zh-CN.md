## 1. 范围与术语

YNX 当前有两条不同的共识路线。CometBFT `v0.38.23` 配合 YNX ABCI 2.0 应用，是已接受的安全基线。较新的 StreamBFT 实现仅存在于已审阅的候选源码提交中，是默认禁用、经过本地测试的影子候选版本。本文不声称公开网络运行 StreamBFT，该影子候选版本也未集成到上方标明的中央源码中。

第 2 至 17 节先定义中央源码所代表的、已接受的 CometBFT/ABCI 行为。第 18 节单独记录较新的 StreamBFT 影子候选版本。主网参数、无需许可的验证者准入、罚没经济机制、形式化验证产物、公开 StreamBFT 部署和生产环境去中心化，均不在已证明范围内。

规范性术语 `MUST`（必须）、`MUST NOT`（不得）、`SHOULD`（应当）和 `MAY`（可以）描述候选行为。只有在标明的源码提交上，与某项要求直接相关的测试及部署证据通过后，该要求才能成为发布声明。

## 3. 信任与故障模型

CometBFT 提供共识网络、提案、投票、提交和验证者集合机制。YNX 应用假定已配置的验证者集合与密钥绑定真实可信。四角色候选方案使用 `primary`、`singapore`、`silicon-valley` 和 `seoul` 作为运营身份；这些名称不能证明所有权独立，也不能证明地理去中心化。

候选方案的安全性依赖于：

- CometBFT 的法定人数假设对所配置投票权成立；
- 创世配置与迁移锚点逐字节一致；
- Ed25519 验证者密钥绑定正确；
- 应用执行具有确定性；
- 持久化的已提交状态完整；
- 运营者与主机访问受到保护；
- 拒绝格式错误、重放、未授权或链不匹配的操作。

本地四验证者故障测试证明，在一个本地验证者及其 ABCI 进程停止后，仍可继续出块。它不能证明互联网分区、相关主机同时故障、拜占庭运营者行为、公开入口遭受拒绝服务攻击，或达到法定投票权的节点被攻破时的行为。

## 4. 迁移锚点

应用从版本 1 的 `ConsensusMigrationState` 启动。迁移文档包含：

- 来源格式 `ynx-devnet-state-v1`；
- 网络身份；
- 最近已提交高度和区块哈希；
- 按地址排序且唯一的账户；
- 按地址排序且唯一的验证者；
- 资源政策；
- 可用和质押 YNXT 总量；
- 确定性状态哈希。

每个账户的余额、质押、资源使用量和批次数量必须非负。可用及质押总量必须与账户之和一致，且不得发生整数溢出。每个验证者必须具有唯一身份、正投票权；存在共识密钥绑定时，该绑定必须有效。必须至少存在一个具有正投票权的活跃验证者。

迁移哈希绑定规范化的迁移内容。ABCI 应用必须拒绝格式错误、未排序、不匹配或哈希不一致的迁移。初始 AppHash 等于通过验证的迁移状态哈希。

## 5. 验证者身份与密钥保管

共识公钥使用 Comet/Tendermint Ed25519 密钥类型。生产清单必须且只能包含获准的活跃角色，并必须拒绝角色缺失、重复项、公钥格式错误、角色绑定错误、非正投票权、重复端点、使用公网或回环地址的私有 P2P 配置，以及派生地址不匹配。

每个运营者在分配的主机上生成验证者和节点私钥。私钥文件必须仅允许指定所有者读取，不得打印、提取到证据包、提交到源码，或通过聊天发送。密钥检查器在本地派生公开身份，并与获准清单比较。

覆盖网络的密钥生成流程和 WireGuard 部署是独立的运营关卡。创建覆盖网络密钥并不授权修改路由；部署覆盖网络也不授权切换公开共识。

## 6. 原生交易信封

版本 1 原生交易是单个严格的 JSON 值，大小不得超过 16 KiB。未知字段和尾随 JSON 值会被拒绝。

| 字段 | 约束 |
| --- | --- |
| `version` | 精确为 `1` |
| `chainId` | 为正且等于配置的链 ID |
| `type` | 精确为 `transfer` |
| `from` | 规范的小写 EVM 兼容地址 |
| `to` | 规范的小写 EVM 兼容地址，且不同于发送方 |
| `amount` | 状态边界内的正有符号 64 位整数 |
| `fee` | 当前受限模型中精确为 `1` 个 YNXT 单位 |
| `nonce` | 为正且等于权威状态中的账户下一 nonce |
| `publicKey` | 十六进制编码的压缩 secp256k1 公钥 |
| `signature` | 十六进制编码的 DER ECDSA 签名，具有规范的 low-S 值 |

原生地址的生成方式是：对去掉格式前缀的未压缩 secp256k1 公钥计算传统 Keccak-256，取最后 20 字节。派生地址必须等于 `from`。

签名字节是上述字段的规范 JSON，不含签名字段，域为 `YNX_NATIVE_TX_V1`。使用提供的 secp256k1 密钥验证这些字节的 SHA-256 摘要。链不匹配、发送方与密钥不匹配、签名不规范、向自己转账、金额无效、费用不匹配、nonce 过旧或超前、余额不足，或重放，都必须拒绝执行。

## 7. 应用操作信封

应用还支持带签名和域隔离的操作信封，用于受限 AI 权限、Pay、Resource、治理、Trust、IDE 及相关状态。每种操作类型定义自己的载荷验证、签名者权限、幂等性、到期、费用和审计行为。某种操作类型存在，并不意味着它授权了超出精确已提交状态转换的外部服务商操作或用户资产转移。

应用操作必须具有确定性，并且必须拒绝未知操作类型、链不匹配的签名、重放、格式错误的标识符、未授权状态转换、作用域扩大、过期批准和不一致的幂等输入。

## 8. ABCI 交易生命周期

### 8.1 CheckTx

`CheckTx` 克隆已提交执行状态，并在不持久化的情况下应用候选交易。有效交易返回成功、确定性的交易哈希数据，以及当前实现所表示的受限 gas 记账。验证或状态转换错误返回非零代码，且不修改状态。

交易内存池接受不等于最终性。通过 `CheckTx` 的交易之后仍可能被排除，或因更早提交的交易改变了相关 nonce、余额、权限或幂等状态而失效。

### 8.2 PrepareProposal

`PrepareProposal` 从已提交状态开始，按顺序评估候选交易。只有满足以下条件，交易才会被纳入：

- 如果提供的交易最大字节上限为正，交易符合该上限；
- 解码和签名检查通过；
- 在所有已选交易之后应用该交易能够成功。

无效或过大的候选交易会被跳过。所选顺序是传入顺序经过确定性筛选后的结果；当前实现不声称具备公开费用拍卖或最大可提取价值政策。

### 8.3 ProcessProposal

对于非零高度，如果它不精确等于下一个高度，`ProcessProposal` 会拒绝。它从已提交状态开始，按顺序重放每笔提案交易。任何一笔交易失败都会导致整个提案被拒绝。只有完全有效的有序列表才会被接受。

### 8.4 FinalizeBlock

`FinalizeBlock` 要求高度连续递增；当另一个已最终确定的状态仍等待提交时，它拒绝最终确定新区块。它按顺序评估交易，发出逐笔交易结果和受限事件，封存确定性的候选状态，并返回所得 AppHash。

实现会记录失败的执行结果，但不应用其状态变化。预期提案处理会在最终确定前拒绝这些交易；测试与远程证据必须能够发现提案验证和最终确定行为之间的差异。

### 8.5 Commit

`Commit` 要求存在等待提交的已最终确定状态。状态经过验证后，以原子方式写入配置的持久状态文件。只有持久化成功后，待提交状态才成为已提交状态。写入失败必须使此前内存中的已提交状态继续保持权威地位。

## 9. 确定性状态与 AppHash

已提交状态的版本 7 在 `YNX_ABCI_STATE_V7` 域下绑定迁移状态哈希、链 ID、已排序账户状态、应用记录及审计数据。哈希文档覆盖账户；AI 权限、操作与审计；Pay 记录；Resource 记录与赞助；治理与 Trust 记录；受限合约记录；EVM 回执与日志；以及 IDE 幂等性。

高度会持久化以支持重启恢复，但不计入 AppHash。因此，没有改变应用状态的空块保留前一个 AppHash。状态验证器检查身份唯一且已排序、数值非负、转换特定的不变量、可用加质押 YNXT 总量守恒、迁移绑定，以及 AppHash 的精确复现。

处理相同迁移锚点和相同有序交易的节点，必须生成逐字节等价的已提交应用状态，以及相同的 AppHash。

## 10. 供应量、费用与账户不变量

原生转账执行必须：

- 保持可用与质押 YNXT 总量不变；
- 从发送方扣除金额加精确的当前费用；
- 向接收方增加对应金额；
- 按当前确定性的验证者规则分配费用；
- 将发送方 nonce 精确递增一次；
- 更新资源使用量，且不得出现负值；
- 按确定性的排序顺序移动可追溯批次。

固定费用和当前费用接收方规则属于测试网实现细节，不是最终经济政策。任何费用市场或验证者经济机制升级，都需要新版本、兼容计划、测试、迁移、治理批准和发布披露。

## 11. 查询行为

ABCI 查询路径提供受限的已提交视图，涵盖迁移与状态、账户、AI、Pay、Resource Market、治理、Trust、受限 IDE 合约与调用、EVM 回执和日志，以及透明度记录。查询必须返回已提交状态，不得修改状态。未知路径会失败，并明确提示支持的接口范围。

Gateway、Indexer、Explorer 或第三方缓存都是派生视图。它们必须注明来源、观察时间、版本及过期或不可用状态，不得覆盖权威的已提交状态。

## 12. 打包与部署边界

候选生成器产出仅含公钥的包，其中包含迁移锚点、共同创世配置、逐角色配置、候选专用服务单元，以及安装、健康检查、备份和回滚脚本。SHA-256 校验覆盖包内每个文件。

候选 RPC、ABCI 和指标端点绑定回环地址。P2P 绑定获准的私有地址。候选服务使用不同的名称和数据根目录，在经批准的切换操作前，不得替换权威服务。

生成包和部署演练证明的是输入验证与打包，而不是远程安装、在线法定人数、容错性、公开入口或公开可用性。

## 14. 安全边界

- CometBFT 共识密钥与用户 secp256k1 交易密钥分离。
- 候选主机密钥和覆盖网络密钥保留在所属主机，并限制文件权限。
- ABCI 不存储用户私钥。
- 公开 RPC 不意味着能够访问管理、ABCI、指标或签名者路径。
- 已签名的公开交易字节可以经过 Gateway；原始私钥不可以。
- 运营者批准标志只授权指明的受限操作。
- 证据采集必须隐藏秘密，同时保留公开身份、交易哈希、高度、区块哈希、发布身份和摘要。

## 15. 恢复与回滚

安装或切换前，运营者必须备份权威状态、配置和发布身份。恢复时，必须先验证状态完整性与网络身份，再启用服务。候选检查失败时，必须保留或恢复权威服务。只有重新验证链推进、账户状态、发布身份、监控和公开路由后，回滚才算完成。

重启持久化不等于恢复演练。发布声明需要记录备份创建、隔离恢复、完整性比较、恢复时间证据、恢复点证据和清理。

## 16. 已知限制与待审阅事项

- StreamBFT 当前组合使用 CometBFT 与 YNX ABCI 应用；不声称已有独立的形式化共识证明。
- 指定名称的四角色拓扑不能证明验证者所有权独立。
- 当前固定费用不是拥堵市场。
- 本文未规定无需许可的验证者接入、委托经济机制、解除绑定、罚没、暂停验证资格、奖励及治理。
- 互联网分区、拜占庭验证者、公开拒绝服务、存储损坏、长距离恢复和升级互操作性测试，仍需更多证据。
- 公开部署和公开交易证据与具体发布版本绑定，不得根据本地或运营者控制的测试推断。

## 18. StreamBFT 影子候选版本

已审阅的影子候选版本将数据可用性、排序和执行分离。它不属于已接受的中央基线，不得投票、提交或改变权威的公开状态。

### 18.1 数据可用性与排序

工作节点形成规范化的 DAG 批次。只有当代表所配置验证者投票权超过三分之二的 Ed25519 投票绑定该批次摘要后，批次才可参与排序。排序使用确定性的领导者轮换、域隔离的法定人数证书、持久化的锁定 QC 投票，以及three-certified-chain 提交判定条件。异步回退使用独立的证书域。候选版本 1 不信任聚合签名或门限签名，仍要求逐个验证 Ed25519 签名。

### 18.2 语义通道

交易按确定性顺序分配到九条固定通道：

1. 共识与治理；
2. 预言机、跨链桥与风险；
3. 清算；
4. 取消与批量取消；
5. 交易订单；
6. Pay 与稳定结算；
7. 通用 EVM；
8. 服务结算；
9. 批量数据承诺。

每条通道都有独立的容量和最低费用配置。规范排序将取消操作放在新交易订单之前。通用 EVM 通道饱和时，不得消耗共识与恢复通道或 Pay 通道的预算。

### 18.3 确定性并行执行

交易声明唯一且已排序的读集合与写集合。候选实现拒绝空的、过大的、未排序的、重复的或未声明的写入键。互不冲突的交易可以并发执行；写入按确定性的依赖批次提交。顺序执行路径执行同一提案。差分测试要求，在不同工作线程数量下，并行与顺序执行的状态根一致。

资源计量覆盖计算、存储读取、存储写入、带宽和状态增长，并检查溢出。状态根对带长度定界且已排序的键进行哈希。

### 18.4 候选局部费用市场

每条通道可维护受限基础费，由之前的基础费、目标计算使用量、观察到的计算使用量、变化分母，以及配置的最小值和最大值推导。资源成本是各项计量资源单位乘以配置价格后，经过检查的总和。发生溢出时必须拒绝执行。

该机制仅为候选代码。它不是已启用的费用政策，未集成到中央共识状态中，没有治理启用，也没有公开费用或销毁证据。

### 18.5 晋级条件

候选模式为 `disabled`、`shadow` 和 `canary`。除非下列所有直接证据类别均为 true，否则 Canary 模式判定会回退到 Shadow：

- 形式化安全验证；
- 差分重放与状态根一致；
- 4、7、13 和 21 个验证者的数量证据；
- 至少三个广域网地区；
- 拜占庭、分区与丢包、状态同步与恢复、长期运行及回滚测试；
- 相对于已接受的 CometBFT 基线，具有综合运营优势。

当前仓库证据明确未满足这一晋级条件。存在针对四个验证者和一个拜占庭验证者的有限 TLA+ 模型源码，但尚未找到 TLC 或 Apalache 的运行产物；模型源码本身不是形式化验证证据。
