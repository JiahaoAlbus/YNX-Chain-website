## 1. 範囲と用語

YNX には現在、異なる2つのコンセンサス開発系列があります。YNX ABCI 2.0 アプリケーションと CometBFT `v0.38.23` の組み合わせが、受け入れ済みの安全性基準です。より新しい StreamBFT 実装は、レビュー済みの候補ソースコミット上で、デフォルトでは無効で、ローカルテストのみが行われたシャドー候補として存在します。公開ネットワークで StreamBFT が稼働しているとは主張せず、このシャドー候補は上記の中央ソースに統合されていません。

第2節から第17節では、まず中央ソースが表す受け入れ済みの CometBFT/ABCI の動作を定義します。第18節では、新しい StreamBFT シャドー候補を別に記録します。Mainnet のパラメータ、許可不要のバリデーター参加、スラッシングの経済設計、形式検証の成果物、公開 StreamBFT デプロイ、本番での分散性は、証明された範囲に含まれません。

規範用語 `MUST`（必須）、`MUST NOT`（禁止）、`SHOULD`（推奨）、`MAY`（任意）は、候補版の動作を記述します。要件をリリースの事実として主張できるのは、特定されたソースコミットで、直接関連するテストとデプロイの証拠が合格した後だけです。

## 3. 信頼と障害のモデル

CometBFT は、コンセンサスのネットワーク通信、提案、投票、コミット、バリデーターセットの仕組みを提供します。YNX アプリケーションは、設定されたバリデーターセットと鍵の結び付けが真正であることを前提とします。4ロールの候補版は `primary`、`singapore`、`silicon-valley`、`seoul` を運用上の識別名として使用します。これらのラベルは、独立した所有や地理的な分散を証明しません。

候補版の安全性は、次の条件に依存します。

- 設定された投票権に対して、CometBFT のクォーラムの前提が成り立つこと。
- ジェネシスと移行アンカーがバイト単位で一致すること。
- Ed25519 バリデーター鍵が正しく結び付けられていること。
- アプリケーションの実行が決定的であること。
- 永続化されたコミット済み状態の整合性。
- 保護された運用者およびホストへのアクセス。
- 不正形式、リプレイ、権限のない操作、異なるチェーン向けの操作を拒否すること。

ローカルの4バリデーター障害テストは、1つのローカルバリデーターとその ABCI プロセスを停止した後もブロック生成が続くことを証明します。インターネットの分断、相関したホスト障害、ビザンチンな運用者の動作、公開入口へのサービス拒否攻撃、投票権クォーラムの侵害における動作を確立するものではありません。

## 4. 移行アンカー

アプリケーションは、バージョン1の `ConsensusMigrationState` から起動します。移行文書には次の内容が含まれます。

- ソース形式 `ynx-devnet-state-v1`。
- ネットワークの識別情報。
- 最後にコミットされた高さとブロックハッシュ。
- アドレス順に並んだ、重複のないアカウント。
- アドレス順に並んだ、重複のないバリデーター。
- リソース方針。
- 流動 YNXT とステーキング済み YNXT の総量。
- 決定的な状態ハッシュ。

すべてのアカウントの残高、ステーク、リソース使用量、ロット金額は非負でなければなりません。流動分とステーキング済み分の集計値は、整数オーバーフローなしにアカウントの合計と一致しなければなりません。すべてのバリデーターは一意の識別情報、正の投票権を持ち、コンセンサス鍵の結び付けが存在する場合はそれが有効でなければなりません。正の投票権を持つアクティブなバリデーターが、少なくとも1つ存在しなければなりません。

移行ハッシュは、正規化された移行内容を結び付けます。ABCI アプリケーションは、不正形式、未整列、不一致、ハッシュ不整合の移行を拒否しなければなりません。初期 AppHash は、検証済みの移行状態ハッシュと等しくなります。

## 5. バリデーターの識別情報と鍵管理

コンセンサス公開鍵は、Comet/Tendermint の Ed25519 鍵型を使用します。本番マニフェストには、承認されたアクティブなロールを過不足なく含めなければならず、ロールの欠落、重複、不正な公開鍵、誤ったロールの結び付け、非正の投票権、エンドポイントの重複、プライベート P2P 用アドレスとしての公開アドレスまたはループバックアドレス、導出アドレスの不一致を拒否しなければなりません。

各運用者は、割り当てられたホスト上でバリデーターとノードの秘密鍵を生成します。秘密鍵ファイルは、意図された所有者だけが読み取れる必要があり、出力、証拠パッケージへの取り込み、ソースへのコミット、チャット送信をしてはいけません。鍵チェッカーは公開識別情報をローカルで導出し、承認済みマニフェストと比較します。

オーバーレイの鍵生成式と WireGuard のデプロイは、別個の運用ゲートです。オーバーレイ鍵の作成は経路変更の許可を意味せず、オーバーレイのデプロイは公開コンセンサスの切り替えを許可しません。

## 6. ネイティブ取引エンベロープ

バージョン1のネイティブ取引は、16 KiB 以下の厳密な単一 JSON 値です。不明なフィールドと、後ろに続く追加の JSON 値は拒否されます。

| フィールド | 制約 |
| --- | --- |
| `version` | 厳密に `1` |
| `chainId` | 正の値で、設定されたチェーン ID と等しい |
| `type` | 厳密に `transfer` |
| `from` | 正規形式の、小文字の EVM 互換アドレス |
| `to` | 正規形式の、小文字の EVM 互換アドレスで、送信者と異なる |
| `amount` | 状態の範囲内の、正の符号付き64ビット整数 |
| `fee` | 現在の限定モデルでは厳密に `1` YNXT 単位 |
| `nonce` | 正の値で、正式なアカウントの次の nonce と等しい |
| `publicKey` | 16進数でエンコードされた、圧縮 secp256k1 公開鍵 |
| `signature` | 正規の low-S 値を持つ、16進数でエンコードされた DER ECDSA 署名 |

ネイティブアドレスは、形式プレフィックスを除いた非圧縮 secp256k1 公開鍵に対する、従来型 Keccak-256 の最後の20バイトです。導出されたアドレスは `from` と一致しなければなりません。

署名対象のバイト列は、署名を除く上記のフィールドを、ドメイン `YNX_NATIVE_TX_V1` の下で正規 JSON にしたものです。そのバイト列の SHA-256 ダイジェストを、提示された secp256k1 鍵で検証します。チェーンの不一致、送信者と鍵の不一致、非正規の署名、自分自身への送金、不正な金額、手数料の不一致、古い nonce または未来の nonce、残高不足、リプレイは、必ず拒否しなければなりません。

## 7. アプリケーション操作のエンベロープ

アプリケーションは、範囲を限定した AI 権限、Pay、Resource、ガバナンス、Trust、IDE、および関連状態について、署名付きでドメイン分離された操作エンベロープもサポートします。各操作種別は、それぞれのペイロード検証、署名者の権限、冪等性、有効期限、手数料、監査動作を定義します。操作種別が存在するだけでは、厳密なコミット済み状態遷移を超える、外部プロバイダーの操作やユーザー資産の移動は許可されません。

アプリケーション操作は決定的でなければならず、不明な操作種別、異なるチェーン向けの署名、リプレイ、不正な識別子、権限のない遷移、スコープ拡大、期限切れの承認、整合しない冪等性入力を拒否しなければなりません。

## 8. ABCI 取引のライフサイクル

### 8.1 CheckTx

`CheckTx` は、コミット済みの実行状態を複製し、永続化せずに候補取引を適用します。有効な取引には、成功、決定的な取引ハッシュデータ、現在の実装が表す範囲内のガス計算を返します。検証または状態遷移のエラーには、非ゼロのコードを返し、状態を変更しません。

メンプールでの受理はファイナリティではありません。`CheckTx` に合格した取引でも、先にコミットされた取引によって関連する nonce、残高、権限、冪等性の状態が変われば、後で除外されたり無効になったりする可能性があります。

### 8.2 PrepareProposal

`PrepareProposal` はコミット済み状態から開始し、候補取引を順番に評価します。取引を含めるのは、次のすべてを満たす場合だけです。

- 提供された最大取引バイト数が正である場合、その上限内に収まる。
- デコードと署名のチェックに合格する。
- それまでに選択された全取引の後に適用して成功する。

無効な候補やサイズ超過の候補はスキップします。選択順序は、入力順序を決定的にフィルターしたものです。現在の実装は、公開の手数料オークションや最大抽出可能価値の方針を主張しません。

### 8.3 ProcessProposal

`ProcessProposal` は、ゼロでない高さが厳密な次の高さと異なる場合に拒否します。コミット済み状態から、提案された全取引を順番に再実行します。1つでも取引が失敗すると、提案全体を拒否します。完全に有効な順序付きリストだけを受け入れます。

### 8.4 FinalizeBlock

`FinalizeBlock` は連続する次の高さを要求し、別の確定済み状態がコミット待ちである間は、新しいブロックの確定を拒否します。取引を順に評価し、取引ごとの結果と範囲を限定したイベントを出力し、決定的な候補状態を封印し、その結果の AppHash を返します。

実装は、失敗した実行結果について、状態変更を適用せずに記録します。提案処理は、確定前にこれらの取引を拒否することが期待されます。テストとリモートの証拠は、提案検証と確定処理の動作の不一致を検出しなければなりません。

### 8.5 Commit

`Commit` は、コミット待ちの確定済み状態を要求します。状態を検証し、設定された永続状態ファイルへアトミックに書き込みます。永続化が成功した後に限り、保留状態がコミット済み状態になります。書き込み失敗時には、それまでのメモリ内のコミット済み状態を正式な状態として維持しなければなりません。

## 9. 決定的な状態と AppHash

コミット済み状態のバージョン7は、ドメイン `YNX_ABCI_STATE_V7` の下で、移行状態ハッシュ、チェーン ID、整列されたアカウント状態、アプリケーションレコード、監査データを結び付けます。ハッシュ文書の対象は、アカウント、AI 権限・操作・監査、Pay レコード、Resource レコードとスポンサーシップ、ガバナンスと Trust レコード、範囲を限定したコントラクトレコード、EVM レシートとログ、IDE の冪等性です。

高さは再起動時の復旧のために永続化されますが、AppHash からは除外されます。したがって、アプリケーション状態を変更しない空ブロックでは、直前の AppHash が維持されます。状態検証器は、一意で整列された識別情報、非負の値、遷移固有の不変条件、流動分とステーキング済み分を合わせた YNXT の総量保存、移行との結び付け、AppHash の厳密な再現を確認します。

同じ移行アンカーと順序付き取引を処理するノードは、バイト単位で等価なコミット済みアプリケーション状態と、同じ AppHash を生成しなければなりません。

## 10. 供給量、手数料、アカウントの不変条件

ネイティブ送金の実行は、次を満たさなければなりません。

- 流動 YNXT とステーキング済み YNXT の総量を保存する。
- 送信者から、金額と厳密な現在の手数料の合計を差し引く。
- 受信者へその金額を加算する。
- 現在の決定的なバリデータールールに従って手数料を配分する。
- 送信者の nonce を厳密に1回だけ増やす。
- 負の値を生じさせずにリソース使用量を更新する。
- 追跡可能なロットを、決定的に整列した順序で移動する。

固定手数料と現在の手数料受取先ルールは Testnet の実装詳細であり、最終的な経済方針ではありません。手数料市場やバリデーターの経済設計をアップグレードするには、新しいバージョン、互換性計画、テスト、移行、ガバナンス承認、リリース開示が必要です。

## 11. クエリの動作

ABCI のクエリパスは、移行と状態、アカウント、AI、Pay、Resource Market、ガバナンス、Trust、範囲を限定した IDE コントラクトと呼び出し、EVM レシート・ログ、透明性記録について、範囲を限定したコミット済みビューを公開します。クエリはコミット済み状態を返さなければならず、状態を変更してはいけません。不明なパスは、サポート対象を明示するメッセージとともに失敗します。

Gateway、Indexer、Explorer、第三者のキャッシュは派生ビューです。これらは情報源、観測時刻、バージョン、古い・利用不可の状態を示さなければならず、正式なコミット済み状態を上書きしてはいけません。

## 12. パッケージ化とデプロイの境界

候補版ジェネレーターは、移行アンカー、共通ジェネシス、ロールごとの設定、候補版専用サービスユニット、インストール・ヘルス・バックアップ・ロールバックのスクリプトを含む、公開鍵のみのパッケージを生成します。SHA-256 の対象範囲は、パッケージ内の全ファイルを結び付けます。

候補版の RPC、ABCI、メトリクスはループバックで待ち受けます。P2P は承認されたプライベートアドレスで待ち受けます。候補サービスは、別の名前とデータルートを使用し、承認された切り替え作業の前に正式なサービスを置き換えてはいけません。

パッケージ生成とドライランのデプロイが証明するのは、入力検証とパッケージ化です。リモートインストール、稼働中のクォーラム、耐障害性、公開入口、公開可用性を証明するものではありません。

## 14. セキュリティ境界

- CometBFT のコンセンサス鍵は、ユーザーの secp256k1 取引鍵とは別です。
- 候補ホストの鍵とオーバーレイ鍵は、ホスト内にとどめ、ファイルモードによって権限を制限します。
- ABCI はユーザーの秘密鍵を保存しません。
- 公開 RPC は、管理、ABCI、メトリクス、署名器の経路へのアクセスを意味しません。
- 署名済みの公開取引バイト列は Gateway を通過できますが、生の秘密鍵は通過できません。
- 運用者の承認フラグは、名前で指定された範囲限定の作業だけを許可します。
- 証拠収集では、公開識別情報、取引ハッシュ、高さ、ブロックハッシュ、リリースの識別情報、ダイジェストを維持しながら、秘密情報を伏せる必要があります。

## 15. 復旧とロールバック

インストールや切り替えの前に、運用者は正式な状態、設定、リリース識別情報のバックアップを必要とします。復元時には、サービスを有効にする前に、状態の整合性とネットワーク識別情報を検証する必要があります。候補版のチェックが失敗した場合、正式なサービスを保持または復元する必要があります。チェーンの進行、アカウント状態、リリースの識別情報、監視、公開経路を再検証するまで、ロールバックは完了ではありません。

再起動後の永続性は、復元訓練ではありません。リリースの主張には、バックアップの作成、分離された環境への復元、整合性比較、復旧時間の証拠、復旧時点の証拠、後片付けの記録が必要です。

## 16. 既知の制約と未完了のレビュー項目

- 現在の StreamBFT は CometBFT と YNX ABCI アプリケーションを組み合わせたものであり、独立した形式的なコンセンサス証明は主張しません。
- 名前付きの4ロール構成は、バリデーターの独立した所有を証明しません。
- 現在の固定手数料は混雑市場ではありません。
- 許可不要のバリデーター参加、委任の経済設計、アンボンディング、スラッシング、投獄状態、報酬、ガバナンスは、本書では規定しません。
- インターネットの分断、ビザンチンなバリデーター、公開面へのサービス拒否攻撃、ストレージ破損、長期間にわたる復旧、アップグレード時の相互運用性のテストには、追加の証拠が必要です。
- 公開デプロイと公開取引の証拠はリリースごとに異なり、ローカルテストや運用者が管理するテストから推定してはいけません。

## 18. StreamBFT シャドー候補

レビュー済みのシャドー候補は、データ可用性、順序付け、実行を分離します。受け入れ済みの中央基準には含まれず、投票、コミット、正式な公開状態の変更を行ってはいけません。

### 18.1 データ可用性と順序付け

ワーカーは正規の DAG バッチを形成します。バッチは、そのダイジェストに、設定されたバリデーター投票権の3分の2を超える Ed25519 票が結び付いた後にのみ、順序付け可能になります。順序付けには、決定的なリーダーローテーション、ドメイン分離されたクォーラム証明書、永続化されたロック済み QC に基づく投票、3段の認証済みチェーンによるコミット述語を使用します。非同期フォールバックは、別の証明書ドメインを使用します。候補版バージョン1は集約署名や閾値署名を信頼せず、個別の Ed25519 検証を引き続き要求します。

### 18.2 意味別レーン

取引は、決定的な順序で次の9つの固定レーンに割り当てられます。

1. コンセンサスとガバナンス。
2. オラクル、ブリッジ、リスク。
3. 清算。
4. 取消と一括取消。
5. 取引注文。
6. Pay とステーブル決済。
7. 汎用 EVM。
8. サービス決済。
9. 大量データのコミットメント。

各レーンは独立した容量と最低手数料の設定を持ちます。正規の並べ替えは、新しい取引注文より先に取消を置きます。汎用 EVM が飽和しても、コンセンサス・復旧または Pay レーンの予算を消費してはいけません。

### 18.3 決定的な並列実行

取引は、重複のない整列済みの読み取りセットと書き込みセットを宣言します。候補版は、空、サイズ超過、未整列、重複、未宣言の書き込みキーを拒否します。競合しない取引は並行して実行できます。書き込みは、決定的な依存関係の波ごとにコミットします。逐次経路も同じ提案を実行します。差分テストでは、異なるワーカー数について、並列実行と逐次実行の状態ルートが一致する必要があります。

リソース計測器は、オーバーフローチェックを伴い、計算、ストレージ読み取り、ストレージ書き込み、帯域、状態増加を対象とします。状態ルートは、長さで区切った整列済みのキーをハッシュ化します。

### 18.4 候補版のローカル手数料市場

各レーンは、直前の基本手数料、目標計算使用量、観測された計算使用量、変化率の分母、設定された最小値と最大値から導く、範囲付きの基本手数料を維持できます。リソース費用は、計測したリソース単位に設定価格を掛けた値を、検査付きで合計したものです。オーバーフロー時は必ず拒否します。

この仕組みは候補コードにすぎません。有効な手数料方針ではなく、中央のコンセンサス状態に統合されておらず、ガバナンスによる有効化もなく、公開手数料やバーンの証拠もありません。

### 18.5 昇格ゲート

候補モードは `disabled`、`shadow`、`canary` です。次のすべての直接的な証拠区分が真でない限り、canary の解決結果は shadow に戻ります。

- 形式的な安全性検証。
- 差分リプレイと状態ルートの一致。
- 4、7、13、21 の各バリデーター数に関する証拠。
- 少なくとも3つの WAN 地域。
- ビザンチン、分断・損失、状態同期・復元、長時間連続稼働、ロールバックのテスト。
- 受け入れ済み CometBFT 基準に対する、運用面での総合的な優位性。

現在のリポジトリの証拠は、意図的にこの昇格ゲートを満たしていません。4つのバリデーターと1つのビザンチンバリデーターを対象とする有限 TLA+ モデルのソースは存在しますが、TLC または Apalache の実行成果物は回収されていません。モデルのソースだけでは、形式検証の証拠にはなりません。
