## 直接说明

YNX Chain 是正在进行测试网工程开发的 Web4 第一层生态系统。YNX Web4 是由 YNX Chain 驱动的应用生态，YNXT 是原生测试网资产。YNX Testnet 使用 EVM 链 ID `6423`（`0x1917`）以及 Comet/Cosmos 链 ID `ynx_6423-1`。

本文件中的“Web4”描述项目希望结合的能力：用户控制的账户、受权限约束的应用、可验证执行、关联证据的自动化，以及明确的人类批准。这是 YNX 的产品术语，并不宣称一种新的互联网标准已经得到采用。

YNX 与无关的 Lynx 品牌产品没有关联。

1. 使账户和交易状态具有确定性，其权威结果来自链上执行，而非用户界面或第三方 API；

## 3. 共识架构

共识候选版本固定使用 CometBFT `v0.38.23`，通过 ABCI 2.0 连接 YNX 应用。在候选网络启动前，确定性的迁移导出会固定账户、供应量、验证者及相关应用状态。

共识路径在 `CheckTx` 中验证交易，通过提案处理确定顺序，在 `FinalizeBlock` 中依次执行，并提交得到的应用哈希。持久账户状态和 AppHash 原子写入；磁盘提交失败时，不得推进内存高度。

本地法定人数验证会创建四个独立验证者目录，分别使用不同的 Ed25519 验证者密钥和节点密钥。它检查：

- 一致的 genesis，以及固定高度的区块哈希收敛；
- 预期验证者身份和签名参与情况；
- 通过 CometBFT RPC 提交一笔已签名的 YNXT 转账；
- 停止一个验证者及其应用后，仍能继续提交；
- 已停止验证者重新启动并追赶状态。

该验证属于本地法定人数证据，本身不能证明远程容错或公开去中心化。生产候选软件包不将验证者及节点私钥放入 Git，通过公开身份绑定四个指定运营角色，对每个打包文件计算哈希，并将候选 RPC、ABCI 和指标接口保留在回环地址。远程部署、故障演练、由所有者签名的交易演练、公开入口批准和独立公开证明仍是需要分别完成的操作。

详细行为及限制在发布后的 `docs/whitepaper/STREAMBFT_SPECIFICATION.md` 中规定；在此之前，`chain/consensus/README.md` 和共识测试是工程依据。

## 4. 账户与原生交易

当前原生转账封装采用规范 JSON，并使用 secp256k1 ECDSA 签名。签名者地址是从未压缩公钥派生的小写 EVM 兼容地址。签名域 `YNX_NATIVE_TX_V1` 绑定：

- 封装版本；
- 数字链 ID；
- 交易类型；
- 发送者和接收者；
- 金额和手续费；
- 账户的下一个 nonce；
- 压缩公钥。

应用验证签名，不保存用户私钥。顺序执行保持 YNXT 总供应量不变，递增 nonce 和已计量的带宽使用量，并按确定性顺序移动可追溯批次。当前有明确范围的原生模型使用固定手续费，不能据此证明动态费用市场已经定案。

用户密钥、助记词、任意提款权限、所有者变更权限及可重复使用的生产签名材料，不得转交浏览器、AI 服务商、应用服务或文档系统。

- 仍需独立安全、财务和法律意见；
- 生产签名及商店发布因产品而异，需要直接证明。
