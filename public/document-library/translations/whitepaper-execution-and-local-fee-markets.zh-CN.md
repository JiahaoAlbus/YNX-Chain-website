## 直接回答

YNX Testnet 当前通过已接受的 ABCI 状态机执行确定性的原生转账和受限的已签名应用操作。在当前整数记账模型中，原生转账路径使用精确固定费用：一个 YNXT 单位。较新的源码候选版本增加了已提交的固定费用事件账本，以及默认禁用的 StreamBFT 影子实现，用于按通道划分的局部费用市场。这两个候选版本均未完成中央集成，也未成为已启用的公开政策。

本文区分当前实现事实与候选费用市场的设计要求。本文不承诺主网费用、验证者收入、营收、销毁、回购、价格或收益率。

## 1. 权威执行边界

权威结果是由 AppHash 绑定的、已提交的 ABCI 应用状态。进入交易内存池、Gateway 响应、Indexer 记录、Explorer 视图、钱包预览或第三方 API 都不是最终权威状态。

执行生命周期如下：

1. 严格解码交易信封并验证签名；
2. 针对已提交状态的克隆进行无状态和有状态检查；
3. 确定性地筛选提案并按顺序重放；
4. 在区块最终确定期间依次应用；
5. 验证状态不变量并计算 AppHash；
6. 在新状态成为权威状态前，以原子方式持久提交。

所有交易和操作类型遇到链不匹配、签名者无效、输入格式错误、未授权状态转换、重放、过期 nonce、幂等性不一致、余额或资源不足，以及版本不匹配时，都必须拒绝执行。

## 2. 状态模型

已提交状态的版本 7 包含：

- 账户、可用余额、质押余额、nonce、资源使用量及可追溯批次；
- AI 权限、操作和审计记录；
- Pay 意图、发票、退款、webhook、事件和幂等性记录；
- Resource 报价、委托、租赁、收入、事件、赞助池及审计；
- 治理请求、Trust 证据、标签、申诉、更正及透明度记录；
- 受限合约身份、运行时存储、回执、日志及 IDE 幂等性记录；
- 迁移锚点和 AppHash。

凡是顺序会影响哈希的集合，都必须规范化，或验证其元素唯一且已排序。数值状态须检查负值及有符号 64 位整数溢出。可用 YNXT 与质押 YNXT 之和必须始终等于迁移锚定的总量。

高度会持久化以支持重启恢复，但不计入 AppHash；如果空块没有改变应用状态，其 AppHash 保持不变。

## 3. 原生转账执行

有效的原生转账绑定链 ID、发送方、接收方、金额、精确费用、下一个 nonce、压缩格式的 secp256k1 公钥，以及规范的 low-S DER 签名。其状态转换如下：

```text
require sender != recipient
require amount > 0
require fee == 1
require nonce == sender.nonce + 1
require sender.balance >= amount + fee

sender.balance    := sender.balance - amount - fee
recipient.balance := recipient.balance + amount
feeRecipient      := deterministic current validator recipient
feeRecipient.balance := feeRecipient.balance + fee
sender.nonce      := nonce
```

实现还会更新受限资源使用量，并确定性地移动可追溯批次。状态验证会拒绝任何总供应量变化。

这一路径中标为“YNXT”的整数，是当前原生模型对外提供的运行时记账单位。公开界面不得悄悄将其重新解释为法币价值，也不得声称存在某个兑换汇率。

## 4. 应用操作执行

已签名应用操作扩展了确定性状态，涵盖 AI 批准、Pay、Resource、治理、Trust，以及受限开发工作流。每种操作都有特定的签名文档与验证规则。根据类型，操作可能绑定签名者、账户、会话、作用域、用途、到期时间、对象版本、幂等键、证据哈希、金额或资源上限。

操作记录不能证明超出其权威范围的外部事件。例如：

- AI 批准记录不能证明模型调用成功；
- 稳定币意图不会执行铸造或销毁；
- 跨链桥协调器的最终确定记录不能证明外部链转账；
- 在已提交交易与 Pay 意图匹配之前，该意图不能证明结算完成；
- 证据哈希不能证明外部法律审阅或审计已经发生。

## 5. 受限合约执行

当前开发路径包含针对明确支持的合约工作流、固定构建产物的受限 EVM 子集执行。它记录已部署字节码身份、源码哈希、运行模式、回执、日志、存储、交易哈希、区块高度和审计哈希。

这不代表与完整以太坊虚拟机等价。尚未支持的操作码、无界执行、任意字节码假设、通用 gas 等价性，以及与所有以太坊工具兼容，均不在已证明的子集范围内。

## 6. 当前费用类别

| 操作 | 当前工程规则 | 发布层面的含义 |
| --- | --- | --- |
| 原生签名转账 | 精确费用为 `1` 个 YNXT 单位 | 已实现的受限测试网规则；不是市场报价 |
| 本地 Devnet 合约部署 | 实用型 Devnet 路径的精确费用为 `10` 个 YNXT 单位 | 仅用于开发；不能证明 ABCI 生产候选版本的最终费用政策 |
| 已签名应用操作 | 在已定义的地方采用类型特定的预期费用 | 必须按操作及源码版本披露 |
| 第三方服务商调用 | 服务商成本与协议费用分开 | 必须注明服务商、费率来源、观察时间、估算或实际类别及失败状态 |
| 交易场所或托管操作 | 不推断任何通用费用 | 需要已接受的服务商或交易场所政策及用户批准 |

费用必须在批准前展示，包含计价单位、金额、接收方或分配规则、可退还性、网络及信息时效。服务不得隐藏价差，也不得将服务商成本转化为未披露的协议费用。

## 7. 局部费用市场的定义

局部费用市场在一个受限领域内对稀缺执行或数据容量定价，而不是要求所有领域共享一次全局竞价。已审阅的 StreamBFT 影子候选版本在本地实现了受限的按通道基础费转换和资源费用运算。它仍处于禁用状态，不在已接受的中央基线中，且没有治理启用或公开证据。

实现之前，每个市场都必须定义：

| 维度 | 必需的决策与证据 |
| --- | --- |
| 资源 | 精确计量单位：字节、步骤、存储、带宽、服务商调用或其他有版本的单位 |
| 领域 | 在同一市场中竞争的交易或操作 |
| 价格形成 | 基础费、标价、拍卖、配额或混合公式 |
| 优先级 | 排序规则及抵御操纵的方式 |
| 限制 | 每区块、每账户、每产品及全局上限 |
| 用户保护 | 最高授权费用、到期、取消及报价过期时的行为 |
| 分配 | 验证者、协议、服务商、补贴、退款及销毁的处理 |
| 失败 | 拒绝、回滚、超时或结果未知时的收费处理 |
| 拥堵 | 调整间隔、边界及突增后的恢复 |
| 升级 | 版本协商、旧客户端行为、迁移、回滚及治理 |

## 8. 候选定价约束

未来的费用函数必须基于已提交输入进行确定性计算，或绑定具有明确到期时间的权威签名报价。在共识执行期间，它不得依赖无版本的墙上时钟、非确定性的服务商结果、隐藏的运营者输入，或可变的第三方响应。

如果评估基础费设计，规范必须明确目标使用量 `T`、观察到的父区块使用量 `U`、之前的基础费 `B`、调整分母 `D`，以及硬性最小值和最大值。例如，候选函数：

```text
B_next = clamp(B_min, B_max, B + trunc(B * (U - T) / (T * D)))
```

与已审阅影子候选版本的形式一致，使用经过检查的无符号整数运算和配置边界。它不是当前公开的 YNX 费用规则；在完成集成、模拟、对抗测试、经济审阅、治理批准、迁移及发布举证之前，不得将其用于公开定价声明。

## 9. 公平排序与可提取价值

当前提案者按顺序筛选传入的候选顺序，不声称具备公开费用拍卖、加密交易内存池、批量拍卖、先到先得保证，或最大可提取价值防护。

未来的排序政策必须公布：

- 提案者裁量范围及可观察的排序输入；
- 相同费用交易的处理；
- 替换与取消规则；
- 重放和重复交易处理；
- 私有订单流与区块构建者的边界；
- 三明治攻击、抢先交易、审查和拒绝服务的威胁模型；
- 纳入区块及最终性的测量；
- 监测与申诉流程。

在直接取得这些规则和对抗测试结果的证据前，不得用“FairFlow”声称具备某种性能或公平性。

## 10. 赞助资源与补贴

资源模型包含受限赞助池，具备所有者政策、允许的受益人或作用域、单次与累计上限、到期时间、唯一操作引用、暂停、恢复、撤销、未使用资源释放和审计。赞助消耗获准的资源额度；它不授权任意 YNXT 转移，也不赋予 Gateway 签名身份。

每项补贴必须明确资金来源、预算、符合条件的操作、限额、期间、耗尽后的行为和关闭规则。补贴活动不得被报告为自然营收，也不得在单位经济核算中隐藏。

## 11. 服务商、交易场所与应用费用

YNX 只能披露用户在操作前已看到并接受的费用，例如：

- 协议 gas 或资源费用；
- 交易场所费用；
- 服务商成本；
- 计算或数据费用；
- 订阅费；
- 管理费；
- 用户明确接受的受托服务中采用高水位线机制的业绩报酬。

披露必须注明来源、生效期间、毛额与净额处理、包含和不包含的成本、风险、锁定、退出、网络类别及证据 ID。业绩报酬不得适用于未实现利润，也不得重置高水位线而对同一次收益恢复重复收费。

禁止隐藏价差、伪造成交量、刷量、伪造流动性、保证收益、秘密回购、隐藏铸造或销毁，以及将销毁描述为营收。

## 12. 失败与未知结果

客户端必须区分：

- 提交前被拒绝；
- Gateway 已接受，但尚未在共识中观察到；
- 已进入交易内存池；
- 已纳入区块且成功；
- 已纳入区块但失败；
- 已提交，但暂时未出现在派生索引中；
- 已过期或被替换；
- 因权威验证不可用而结果未知。

结果未知不得触发盲目重复提交。恢复过程应使用已签名交易的哈希、发送方、nonce、预期接收方、金额和费用，对权威状态进行有界的最终性查询。

## 13. 声称动态费用能力前所需的测量

费用市场候选版本至少需要通过可复现的工作负载测量：

- 准入、纳入区块及最终性延迟的 p50、p95、p99；
- 有效与无效交易吞吐量；
- 提案字节数和执行资源饱和情况；
- 交易内存池与应用队列深度；
- 费用波动及用户多付的费用；
- 提案者分配及集中度；
- 垃圾交易成本及合法用户被挤出的情况；
- 状态与索引存储增长；
- 损失一个验证者及网络延迟时的行为；
- 跨费用政策版本边界时，旧客户端与回滚的行为。

报告必须包含硬件、拓扑、数据集、持续时间、预热、源码提交、配置、错误、原始输出及置信度或覆盖范围。本地四节点测试不能外推为公开生产容量。

## 14. 升级与兼容性

费用政策变更会影响共识。发布必须包含：

1. 新的政策与模式版本；
2. 启用高度及治理授权；
3. 旧客户端响应及交易拒绝行为；
4. 确定性迁移及回滚迁移；
5. 钱包费用预览兼容性；
6. Indexer、Explorer、SDK、交易所及托管更新；
7. 监控阈值及紧急暂停条件；
8. 公开发布说明及被替代政策的引用。

任何运营者或 AI 系统都不得悄悄修改费用、发行量、金库分配或风险限额。
