## 要点

YNX Chain は、Testnet のエンジニアリングを継続的に進めている Web4 レイヤー1のエコシステムです。YNX Web4 は YNX Chain を基盤とするアプリケーションのエコシステムです。YNXT は Testnet のネイティブ資産です。YNX Testnet は EVM チェーン ID `6423`（`0x1917`）と Comet/Cosmos チェーン ID `ynx_6423-1` を使用します。

本書の「Web4」は、ユーザーが管理するアカウント、許可に基づくアプリケーション、検証可能な実行、証拠に結び付いた自動化、明示的な人間の承認を組み合わせるというプロジェクトの構想を表します。YNX の製品用語であり、新しいインターネット標準が採用されたという主張ではありません。

YNX は、無関係な Lynx ブランドの製品とは提携していません。

## 1. 設計目標

YNX Chain は、範囲を限定した次の5つの目標に沿って開発されています。

1. 正式な結果がユーザーインターフェースや第三者 API ではなく、チェーンの実行から得られる、決定的なアカウント状態と取引状態。
2. ユーザーの資産管理、アプリケーションの権限、サービス運用、プロトコルの権限の明示的な分離。
3. 決済、信頼、リソース、開発、AI 支援ワークフローのための、証拠に結び付いたアプリケーション。
4. バージョン管理された状態、観測可能な障害、バックアップとロールバックの手順を備えた、復旧可能な運用。
5. 実装、テスト、インストール、統合、ステージング、公開、署名、配布の各状態を区別する、正確なリリース開示。

現在の開発範囲は、インターネット規模の処理能力、許可不要のバリデーター参加、Mainnet の経済設計、本番での資産管理、ステーブルコインの準備資産、ブリッジの流動性、取引所の流動性、継続的な公開可用性を証明するものではありません。

## 3. コンセンサスのアーキテクチャ

コンセンサス候補版は CometBFT `v0.38.23` に固定され、ABCI 2.0 を介して YNX アプリケーションと接続します。候補版の起動前に、決定的な移行エクスポートによってアカウント、供給量、バリデーター、および関連するアプリケーション状態の基準が確定されます。

コンセンサス経路では、`CheckTx` で取引を検証し、提案処理によって順序を決め、`FinalizeBlock` で逐次適用し、その結果のアプリケーションハッシュをコミットします。永続的なアカウント状態と AppHash はアトミックに書き込まれます。ディスクへのコミットが失敗した場合、メモリ内の高さを進めてはいけません。

ローカルのクォーラム検証ゲートは、異なる Ed25519 のバリデーター鍵とノード鍵を持つ、4つの独立したバリデーターホームを作成します。次の項目を確認します。

- 共通のジェネシスと、固定された高さにおけるブロックハッシュの一致。
- 想定されるバリデーターの識別情報と署名者の参加。
- CometBFT RPC を介した、署名付き YNXT 送金。
- 1つのバリデーターとそのアプリケーションを停止した後もコミットが続くこと。
- 停止したバリデーターの再起動と追いつき。

このゲートは、ローカルのクォーラムに関する証拠です。それ自体でリモート環境の耐障害性や公開ネットワークの分散性を証明するものではありません。本番候補パッケージは、バリデーターとノードの秘密鍵を Git に含めず、公開識別情報で4つの名前付き運用者ロールを結び付け、パッケージ内の全ファイルをハッシュ化し、候補版の RPC、ABCI、メトリクスをループバックに限定します。リモートデプロイ、障害訓練、所有者が署名する取引訓練、公開入口の承認、独立した公開証明は、それぞれ別の作業として扱います。

詳細な動作と制約は、公開時には `docs/whitepaper/STREAMBFT_SPECIFICATION.md` に規定されます。それまでは、`chain/consensus/README.md` とコンセンサステストが開発上の根拠です。

## 4. アカウントとネイティブ取引

現在のネイティブ送金エンベロープは、secp256k1 ECDSA で署名された正規 JSON です。署名者のアドレスは、非圧縮公開鍵から導出される、小文字の EVM 互換アドレスです。署名ドメイン `YNX_NATIVE_TX_V1` は次の項目を結び付けます。

- エンベロープのバージョン。
- 数値のチェーン ID。
- 取引種別。
- 送信者と受信者。
- 金額と手数料。
- アカウントの次の nonce。
- 圧縮公開鍵。

アプリケーションは署名を検証し、ユーザーの秘密鍵を保存しません。逐次実行は YNXT の総供給量を保持し、nonce と計測された帯域使用量を増やし、追跡可能なロットを決定的な順序で移動します。現在の限定されたネイティブモデルは固定手数料を使用しており、確定済みの動的手数料市場を示す証拠ではありません。

ユーザーの鍵、シードフレーズ、任意の出金権限、所有者変更権限、再利用可能な本番署名用の秘密情報を、ブラウザー、AI プロバイダー、アプリケーションサービス、ドキュメントシステムに渡してはいけません。

## 5. 実行と EVM 互換性

YNX Testnet は、JSON-RPC の要件、Hardhat と Foundry の設定、コントラクト検証ワークフロー、SDK ヘルパー、サンプルコントラクトを含む、EVM 向けのネットワークメタデータと開発ツールを公開しています。互換性は、現在のテストと公開証拠によって直接検証されたメソッドと動作に限定されます。すべての Ethereum クライアント、オペコード、ウォレット、インデクサー、取引所、ブリッジ、分散型アプリケーションとの普遍的な互換性を意味しません。

デプロイ、オンチェーンのバイトコード、ソース検証、チェーンの識別情報、小数桁数、シンボル、発行者の権限を直接確認するまで、コントラクトアドレスを公開トークンリストや連携ガイドに載せてはいけません。そのため、これらの条件が満たされない限り、正規の Testnet トークンリストは空のままです。

## 6. 手数料とリソース計算

現在の Testnet 開発モデルでは、YNXT をネイティブ取引手数料とリソース計算に使用します。コミット済みのネイティブ送金実装は厳密な固定手数料を使用し、現在のバリデータールールに従ってその手数料を割り当てます。これは限定されたランタイムの実装上の事実であり、将来の手数料水準、バリデーター収入、トークン価値、利回り、Mainnet 方針の約束ではありません。

将来のローカル手数料市場は、次の事項を定義し、バージョン管理し、テストする必要があります。

- 計測対象の単位。
- 基本手数料またはオークションの計算。
- 混雑と優先順位の扱い。
- 提案者とプロトコルへの配分。
- 丸め処理と通貨単位のルール。
- ユーザーが承認する最大費用。
- 失敗した取引の扱い。
- スパムおよびサービス拒否攻撃への耐性。
- アップグレードとロールバックの互換性。

本ホワイトペーパーは、収益、バーン、買い戻し、年利回り、収益性を主張しません。これらを主張するには、期間を特定した総額と純額、費用、リスク、ドローダウン、ロックと退出の条件、ネットワーク区分、証拠 ID、および保証しない旨の明示が必要です。

## 7. ステーキングとバリデーターのセキュリティ

移行パッケージとコンセンサスパッケージは、候補ネットワークに必要なバリデーターの識別情報とステーキング状態を表現します。完全な公開ステーキング仕様では、委任、アンボンディング、報酬、コミッション、スラッシング、投獄状態、ガバナンス権限、鍵のローテーション、バリデーターの退出、状態移行を個別に定義する必要があります。バリデーターレコードが存在するだけでは、これらの経済ルールは確定しません。

リキッドステーキングとセーフティモジュールは、コントラクトまたはランタイムロジック、監査、デプロイ、資産管理の境界、流動性、出金経路、支払不能時の対応、インシデント制御について直接の証拠が得られるまでは、設計候補にすぎません。ステーキング APY やリキッドステーキングの償還を約束するものではありません。

## 8. Wallet、認証、アプリケーション権限

想定される共通の信頼経路は、長期間有効なブラウザーの bearer トークンや製品固有の互換ログインではなく、正規の Wallet 承認と製品範囲に限定された Gateway セッションを使用します。完全に受け入れられるフローは、製品 ID、バンドル ID、デバイス鍵、ユーザーアカウント、スコープ、有効期限、チャレンジ、承認、イントロスペクション、失効、監査記録を結び付けます。

各検証器は、リプレイ、改ざん、製品の不一致、バンドルの不一致、デバイスの不一致、スコープ拡大、有効期限切れ、失効に対して、必ず拒否側に閉じる必要があります。製品候補は、受け入れられたプロトコルとこれらの異常系が中央のリリース系列で合格するまで、中央統合済みとは記述しません。

アプリケーションは範囲を限定した操作を要求できますが、資産管理権限を引き継ぐことはできません。ユーザー資産を置ける場所は、ユーザーの Wallet、明示的に開示された取引所サブアカウント、ユーザー承認済みの戦略金庫、特定されたカストディ事業者、承認済みプロトコルコントラクトに限られます。戦略への委任には、最小権限、資産と取引場所の許可リスト、金額と頻度の上限、有効期限、nonce ドメイン、即時失効、キルスイッチ、緊急退出、監査可能な受領記録が必要です。

## 9. AI ガバナンス

AI は制約された提案レイヤーです。草案作成、説明、翻訳、要約、調査、プレビュー、シミュレーション、提案、レビュー可能なパッチ生成を行えます。署名、支払い、取引、スワップ、出金、カード開設、メッセージ送信、コンテンツ公開、データ削除、権限変更、リスク変更、発行条件変更、財務資産の操作、コンセンサスのアップグレード、人間の承認の迂回を独立して行ってはいけません。

AI 支援の操作には、コンテキスト利用への同意、プロバイダーとモデルの状態、該当する場合のリソースまたは費用の可視化、プレビュー、承認・拒否の操作、監査記録、正確な失敗時の動作が必要です。テキスト生成の成功は、正式なチェーン、アカウント、残高、取引、決済、Trust 案件、権限の状態を意味しません。

## 10. 決済、取引、クオンツシステム

YNX Pay の開発には、範囲を限定したインテント、請求書、決済検証、受領記録、テストフローが含まれます。公開決済ネットワークには、さらに受け入れ済みの Wallet 連携、加盟店の識別情報、本番運用、返金と紛争への対応、直接の公開証拠が必要です。

Exchange、DEX、クオンツ製品の候補版は、次のルールを維持する必要があります。

- 明示的な運用金庫契約または有料サービス契約で別段の定めがない限り、ユーザーの利益と損失はユーザーに帰属する。
- 手数料は操作前に開示し、承認を得る。
- どのサービスも、スプレッドを隠したり、未実現利益に課金したり、二重請求のために課金基準をリセットしたり、出来高や流動性を捏造したり、収益を保証したりしてはいけない。
- 市場、注文、残高、決済の状態は、正式な情報源と鮮度を明示する。
- AI や戦略エンジンは、ユーザーが署名した委任の範囲を超えてはいけない。

UltraLiquidity と FairFlow は、その仕組み、敵対的モデル、シミュレーション、実測結果、実装、デプロイ、市場の公正性を守る制御が証拠とともに公開されるまで、公開性能についての主張ではありません。

## 11. ステーブルコイン、準備資産、償還

YNX Chain は、USDT、USDC、その他の発行者型ステーブルコインについて、対応、承認、提携を主張しません。ローカルの `ynx-stablecoind` コントロールプレーンはレビューとインテントの状態を記録しますが、実行は無効です。署名器、コントラクト呼び出し、外部取引、ミント、バーン、凍結、差押え、ブラックリスト、資金移動の実装はありません。

ネイティブ YNXT と、プロトコルのステーキング、リソース、財務資産の状態は、発行者による制御の対象として拒否されます。将来のステーブルコイン連携には、特定された発行者、法務および資産管理のレビュー、正規資産と代替表現資産の方針、準備資産の対象範囲、独立した証明、償還条件、手数料、所要時間、停止と支払不能時の扱い、インシデント対応、デプロイ、公開証拠が必要です。

発行者レコード、ガバナンス要求、証拠ハッシュは参照情報であり、準備資産や償還能力の証明ではありません。

## 12. ブリッジ、オラクル、データの境界

ローカルのブリッジコーディネーターは、転送インテントを永続化し、再使用された送信元イベントを拒否し、厳密な冪等性をサポートし、許可リストにある Ed25519 リレイヤーの証明を検証し、設定されたファイナリティと少なくとも2つのリレイヤーを要求し、ハッシュで連鎖した監査証跡を記録します。確定するのはローカルのコーディネーター状態だけです。

外部への送信は無効です。外部チェーンの取引、ミント、バーン、資金のあるブリッジアカウント、本番リレイヤーによる資産管理、リモートブリッジ、公開ブリッジエンドポイント、流動性、プロバイダーの承認を主張しません。

オラクルと市場データの値は、承認済みの YNX プロトコル機構によって書き込まれた場合を除き、第三者データまたは派生データです。各データレコードは、情報源、観測時刻、バージョン、意味のある場合の対象範囲または信頼度、および明示的な古い・利用不可・エラーの状態を示す必要があります。第三者データは、YNX Wallet の識別情報、チェーン状態、残高、権限、取引、決済、受領記録、Trust 案件の代わりにはなりません。

## 13. Trust、異議申立て、市場の公正性

Trust アーキテクチャは、証拠、要求の有効性、拒否理由、異議申立て、訂正、透明性を明示的な状態として扱います。どのインターフェースや外部プロバイダーも、申し立て、モデルのスコア、キャッシュ値、第三者のラベルを、黙って正式な執行判断へ変換してはいけません。

ユーザーのアクセスや資産に影響する制御には、定義された権限、範囲、証拠の参照、発効時刻、有効期限またはレビュー日、異議申立て経路、訂正経路、監査識別子が必要です。ネイティブ YNXT に対する発行者型の凍結や差押えは、現在のステーブルコイン用コントロールプレーンの範囲外です。

## 14. 製品アーキテクチャ

YNX Web4 は、明示的なプロトコルでつながる独立した製品群です。Wallet、Social、Pay、Exchange、Shop、Explorer、Developer、AI、Monitor、Trust Center、Resource Market、Browser、Music、Video、Cloud、Docs、Search、Finance、Mail、Calendar は、それぞれ独自の製品 ID と最小権限の結び付けを維持します。共通のチェーン ID は、スーパーアプリや、制限のない共有セッションを正当化しません。

製品群には、成熟度の異なる開発候補が含まれます。実装、テスト、インストール、統合、デプロイ、署名、ダウンロード、ストアの状態を確定できるのは、コンポーネントごとのリリース記録だけです。

## 15. セキュリティとサプライチェーン

リポジトリの基本的な制御には、環境検証、秘密情報と仮置き文言のスキャン、範囲を限定した CORS とレート制限の方針、管理機能の分離、監査ログ、バックアップとロールバックのツール、インシデント手順、依存関係チェック、アップグレード方針、AI の権限制限が含まれます。完全なリリースには、さらに脅威モデル、セキュリティ境界、SBOM、第三者ライセンス表示、ロックファイルのレビュー、ビルドスクリプトの許可リスト、SAST、DAST、コンテナと成果物のスキャン、来歴、再現可能なビルドの証拠が必要です。

公開成果物は、変更不能な URL、SHA-256 ダイジェスト、バイト数、署名区分、最小対応 OS、ソースコミット、および実際のインストールとコールドスタートの証拠を示す必要があります。既知の脆弱性が存在しないことは、監査意見ではありません。

## 16. 運用と復旧

スキーマ、状態、API、設定、成果物には、明示的なバージョンが必要です。リリース運用では、移行、旧クライアントとの互換性、非推奨化、ロールバック移行、バックアップ、復元訓練、エクスポートと削除、保持期間、サービス終了時の退出経路を扱う必要があります。再起動後に状態が残るだけでは、災害復旧とはいえません。

運用上の証拠には、構造化ログ、メトリクス、実装されている場合のトレース、要求・エラー・監査の識別子、ヘルスとバージョンの公開面、アラート、SLO ダッシュボード、インシデント対応、状況の周知、サポート、該当する場合の返金・紛争対応、復旧を含める必要があります。ユーザー向けエラーに、スタック、秘密情報、サーバーパス、プロバイダーの認証情報を露出してはいけません。

## 17. 性能と経済性の証拠

プロジェクトは、小規模なローカルテストから本番の処理能力を外挿してはいけません。処理能力を主張するには、ハードウェア、ソフトウェア、データセット、期間、ソースコミットを記録した上で、p50・p95・p99 のレイテンシー、スループット、同時実行数、キューの動作、ストレージの増加、プロバイダーのレイテンシーとレート制限、コールドスタート、エラー率、可用性、RTO/RPO の実測値が必要です。

ユニットエコノミクスには、アクティブユーザー当たりのインフラとプロバイダーの費用、無料枠、補助、サポート負担、候補サービスの収益、持続可能な粗利シナリオが必要です。推定値は推定として明示し、観測された請求額や使用量と区別する必要があります。

## 18. ガバナンスと変更管理

プロトコル、経済設計、セキュリティ、リリースの変更には、バージョン管理された提案、レビュー権限、互換性分析、テスト証拠、デプロイ承認、ロールバック条件、公開変更記録が必要です。AI は変更の草案作成や説明を行えますが、コンセンサスのアップグレード、発行条件の変更、財務資産の操作、リスク方針の変更を承認または実行することはできません。

Mainnet の有効化には、このリポジトリを超える証拠が必要です。独立したセキュリティレビュー、経済・法務レビュー、バリデーターと鍵生成式の承認、リモート障害・復元訓練、公開ストレステスト、ガバナンスの構築、インシデント対応準備、明示的なリリース承認が求められます。
