## 要点

YNX Testnet は現在、受け入れ済みの ABCI 状態機械を通じて、決定的なネイティブ送金と、範囲を限定した署名付きアプリケーション操作を実行します。ネイティブ送金経路は、現在の整数会計モデルで、厳密に1 YNXT 単位の固定手数料を使用します。より新しいソース候補は、コミット済みの固定手数料イベント台帳と、レーンごとのローカル手数料市場を実装した、無効状態の StreamBFT シャドー実装を追加します。どちらの候補も中央に統合されておらず、有効な公開方針でもありません。

本書は、現在の実装上の事実と、候補となる手数料市場の設計要件を区別します。Mainnet の手数料、バリデーター収入、収益、バーン、買い戻し、価格、利回りを約束するものではありません。

## 1. 正式な実行結果の境界

正式な結果は、AppHash に結び付けられた、コミット済みの ABCI アプリケーション状態です。メンプールへの受理、Gateway の応答、Indexer のレコード、Explorer の表示、ウォレットのプレビュー、第三者 API は、最終的な正式状態ではありません。

実行のライフサイクルは次のとおりです。

1. 厳密なエンベロープのデコードと署名検証。
2. コミット済み状態の複製に対する、状態に依存しないチェックと状態依存のチェック。
3. 決定的な提案フィルタリングと、順序に従った再実行。
4. ブロック確定時の逐次適用。
5. 状態の不変条件の検証と AppHash の計算。
6. 新しい状態が正式なものになる前の、アトミックな永続コミット。

すべての取引種別と操作種別は、チェーンの不一致、不正な署名者、不正形式の入力、権限のない遷移、リプレイ、古い nonce、整合しない冪等性、残高またはリソースの不足、バージョンの不一致に対して、必ず拒否側に閉じる必要があります。

## 2. 状態モデル

コミット済み状態のバージョン7には、次の内容が含まれます。

- アカウント、流動残高、ステーキング済み残高、nonce、リソース使用量、追跡可能なロット。
- AI 権限、操作、監査のレコード。
- Pay のインテント、請求書、返金、Webhook、イベント、冪等性レコード。
- Resource の見積もり、委任、レンタル、収入、イベント、スポンサー付きプール、監査。
- ガバナンス要求、Trust の証拠、ラベル、異議申立て、訂正、透明性。
- 範囲を限定したコントラクトの識別情報、ランタイムストレージ、レシート、ログ、IDE の冪等性。
- 移行アンカーと AppHash。

順序がハッシュに影響するコレクションは、正規化するか、一意で整列されていることを検証します。数値状態については、負の値と符号付き64ビットのオーバーフローを確認します。流動 YNXT とステーキング済み YNXT の合計は、移行アンカーが定める総量と等しいままでなければなりません。

高さは再起動時の復旧のために永続化しますが、AppHash からは除外します。アプリケーション状態を変更しない空ブロックでは、既存の AppHash を維持します。

## 3. ネイティブ送金の実行

有効なネイティブ送金は、チェーン ID、送信者、受信者、金額、厳密な手数料、次の nonce、圧縮 secp256k1 公開鍵、正規の low-S DER 署名を結び付けます。その状態遷移は次のとおりです。

```text
require sender != recipient
require amount > 0
require fee == 1
require nonce == sender.nonce + 1
require sender.balance >= amount + fee

sender.balance    := sender.balance - amount - fee
recipient.balance := recipient.balance + amount
feeRecipient      := deterministic current validator recipient
feeRecipient.balance := feeRecipient.balance + fee
sender.nonce      := nonce
```

実装は、範囲を限定したリソース使用量と、決定的なロット移動も更新します。状態検証は、総供給量のいかなる変化も拒否します。

この経路で「YNXT」と表示される整数は、現在のネイティブモデルが公開するランタイムの会計単位です。公開インターフェースは、それを黙って法定通貨の価値として読み替えたり、為替レートを主張したりしてはいけません。

## 4. アプリケーション操作の実行

署名付きアプリケーション操作は、AI 承認、Pay、Resource、ガバナンス、Trust、範囲を限定した開発者ワークフローのために、決定的な状態を拡張します。すべての操作には、種別固有の署名文書と検証ルールがあります。種別に応じて、操作は署名者、アカウント、セッション、スコープ、目的、有効期限、オブジェクトのバージョン、冪等性キー、証拠ハッシュ、金額、リソース上限を結び付ける場合があります。

操作レコードは、その権限外の外部イベントを証明できません。例えば、次のような区別があります。

- AI 承認レコードは、モデル呼び出しの成功を証明しません。
- ステーブルコインのインテントは、ミントやバーンを実行しません。
- ブリッジコーディネーターの確定は、外部チェーンでの転送を証明しません。
- Pay インテントは、コミット済み取引が一致するまで、決済を証明しません。
- 証拠ハッシュは、外部の法務レビューや監査レビューが行われたことを証明しません。

## 5. 範囲を限定したコントラクト実行

現在の開発者向け経路には、特にサポートされるコントラクトワークフローについて、成果物を固定した、範囲限定の EVM サブセット実行が含まれます。デプロイ済みバイトコードの識別情報、ソースハッシュ、ランタイムモード、レシート、ログ、ストレージ、取引ハッシュ、ブロック高さ、監査ハッシュを記録します。

これは、Ethereum Virtual Machine と完全に等価であるという主張ではありません。未対応のオペコード、無制限の実行、任意のバイトコードに関する前提、普遍的なガス等価性、すべての Ethereum ツールとの互換性は、証明されたサブセットの範囲外です。

## 6. 現在の手数料区分

| 操作 | 現在の開発上のルール | リリース上の解釈 |
| --- | --- | --- |
| ネイティブの署名付き送金 | 厳密に `1` YNXT 単位の手数料 | 実装済みの範囲限定 Testnet ルール。市場の見積価格ではない |
| ローカル devnet のコントラクトデプロイ | 実用的な devnet 経路では、厳密に `10` YNXT 単位の手数料 | 開発専用のルール。ABCI 本番候補の最終手数料方針を示す証拠ではない |
| 署名付きアプリケーション操作 | 定義されている場合、種別固有の想定手数料 | 操作とソースバージョンごとに開示が必要 |
| 第三者プロバイダーの呼び出し | プロバイダー費用はプロトコル手数料とは別 | プロバイダー、料金表の出典、観測時刻、推定・実績の区分、失敗状態を明示する必要がある |
| 取引場所または資産管理に関する操作 | 汎用的な手数料を推定しない | 受け入れ済みのプロバイダー・取引場所の方針とユーザー承認が必要 |

手数料は、通貨単位、金額、受取先または配分ルール、返金可否、ネットワーク、鮮度とともに、承認前に表示する必要があります。サービスは、スプレッドを隠したり、プロバイダー費用を未開示のプロトコル手数料に変えたりしてはいけません。

## 7. ローカル手数料市場の定義

ローカル手数料市場は、すべてのドメインに単一の全体入札を共有させるのではなく、範囲を限定したドメイン内の希少な実行容量またはデータ容量に価格を付けます。レビュー済みの StreamBFT シャドー候補は、範囲付きのレーンごとの基本手数料遷移と、リソース手数料の算術をローカルで実装します。引き続き無効で、受け入れ済み中央基準の外にあり、ガバナンスによる有効化や公開証拠はありません。

実装前に、各市場は次を定義する必要があります。

| 観点 | 必要な決定と証拠 |
| --- | --- |
| リソース | 厳密な計測単位：バイト、ステップ、ストレージ、帯域、プロバイダー呼び出し、または別のバージョン管理された単位 |
| ドメイン | 同じ市場で競合する取引または操作 |
| 価格形成 | 基本手数料、掲示価格、オークション、割当量、またはそれらを組み合わせた式 |
| 優先順位 | 順序付けルールと操作への耐性 |
| 上限 | ブロックごと、アカウントごと、製品ごと、および全体の上限 |
| ユーザー保護 | 承認された最大手数料、有効期限、取消、古い見積もりの扱い |
| 配分 | バリデーター、プロトコル、プロバイダー、補助、返金、バーンの扱い |
| 失敗 | 拒否、巻き戻し、タイムアウト、結果不明の場合の課金の扱い |
| 混雑 | 調整間隔、範囲、急増後の復帰 |
| アップグレード | バージョンネゴシエーション、旧クライアントの動作、移行、ロールバック、ガバナンス |

## 8. 候補価格計算の制約

将来の手数料関数は、コミット済み入力から決定的に計算するか、明確な有効期限を持つ正式な署名付き見積もりに結び付ける必要があります。コンセンサス実行中に、バージョン管理されていない実時間時計、非決定的なプロバイダー結果、隠れた運用者入力、変更可能な第三者応答へ依存してはいけません。

基本手数料の設計を評価する場合、仕様は、目標使用量 `T`、観測された親ブロックの使用量 `U`、直前の基本手数料 `B`、調整分母 `D`、厳格な最小値・最大値を示す必要があります。次のような候補関数は、

```text
B_next = clamp(B_min, B_max, B + trunc(B * (U - T) / (T * D)))
```

検査付きの符号なし整数演算と設定された範囲を用いる、レビュー済みシャドー候補の形式と一致します。これは現在公開されている YNX の手数料ルールではなく、統合、シミュレーション、敵対的テスト、経済レビュー、ガバナンス承認、移行、リリース証拠なしに、公開価格についての主張に使用してはいけません。

## 9. 公正な順序付けと抽出可能価値

現在の提案者は、入力された候補順序を逐次フィルターします。公開手数料オークション、暗号化メンプール、バッチオークション、最初に観測された順序の保証、最大抽出可能価値からの保護を主張しません。

将来の順序付け方針は、次を公開する必要があります。

- 提案者の裁量と、観測可能な順序付け入力。
- 同額手数料の取引の扱い。
- 置換と取消のルール。
- リプレイと重複への対応。
- 非公開注文フローとビルダーの境界。
- サンドイッチ、フロントランニング、検閲、サービス拒否攻撃の脅威モデル。
- 取引包含とファイナリティの測定。
- 監視と異議申立ての手順。

これらのルールと敵対的条件での結果に直接の証拠が得られるまで、「FairFlow」を性能または公正性の主張として使用してはいけません。

## 10. スポンサー付きリソースと補助

リソースモデルには、所有者方針、許可された受益者またはスコープ、操作ごとと累積の上限、有効期限、一意の操作参照、一時停止、再開、失効、未使用リソースの解放、監査を備えた、範囲限定のスポンサー付きプールが含まれます。スポンサーシップは承認されたリソース枠を消費します。任意の YNXT 移動を許可したり、Gateway の署名 ID を付与したりするものではありません。

すべての補助は、資金源、予算、対象操作、上限、期間、使い切った場合の動作、停止ルールを示す必要があります。補助を受けた活動を、自発的に生じた収益として報告したり、ユニットエコノミクスから隠したりしてはいけません。

## 11. プロバイダー、取引場所、アプリケーションの手数料

YNX が開示できるのは、ユーザーが操作前に確認し受け入れた料金だけです。例えば次のものがあります。

- プロトコルのガスまたはリソース手数料。
- 取引場所の手数料。
- プロバイダー費用。
- 計算またはデータの料金。
- サブスクリプション。
- 管理手数料。
- 明示的に受け入れられた運用サービスに対する、ハイウォーターマーク方式の成功報酬。

開示では、出典、有効期間、総額・純額の扱い、含まれる費用と含まれない費用、リスク、ロック、退出、ネットワーク区分、証拠 ID を明記する必要があります。成功報酬を未実現利益に適用したり、ハイウォーターマークをリセットして同じ回復分に二重課金したりしてはいけません。

隠れたスプレッド、架空の出来高、仮装売買、架空の流動性、保証された収益、秘密の買い戻し、隠れたミント・バーン、バーンを収益と説明することは禁止です。

## 12. 失敗と結果不明

クライアントは、次の状態を区別する必要があります。

- 送信前に拒否された。
- Gateway は受け入れたが、コンセンサスでは観測されていない。
- メンプールに受理された。
- 成功としてブロックに含まれた。
- 失敗としてブロックに含まれた。
- コミット済みだが、派生インデックスに一時的に存在しない。
- 期限切れまたは置換済み。
- 正式な検証が利用できないため不明。

結果不明を理由に、無条件の重複送信を行ってはいけません。復旧では、署名済み取引のハッシュ、送信者、nonce、想定受信者、金額、手数料を使用し、正式な状態に対して範囲を限定したファイナリティ検索を行います。

## 13. 動的手数料を主張する前に必要な測定

手数料市場の候補には、少なくとも次を測定する、再現可能なワークロードが必要です。

- 受理、取引包含、ファイナリティの p50・p95・p99 レイテンシー。
- 有効な取引と無効な取引のスループット。
- 提案のバイト数と実行リソースの飽和。
- メンプールとアプリケーションのキューの深さ。
- 手数料の変動性とユーザーの過払い。
- 提案者への配分と集中度。
- スパムの費用と正当なユーザーの排除。
- 状態とインデックスのストレージ増加。
- 1バリデーターの喪失とネットワーク遅延の下での動作。
- 手数料方針のバージョン境界をまたぐ旧クライアントとロールバックの動作。

報告書には、ハードウェア、トポロジー、データセット、期間、ウォームアップ、ソースコミット、設定、エラー、生の出力、信頼度・対象範囲を含める必要があります。ローカルの4ノードテストから、公開本番環境の処理能力を外挿してはいけません。

## 14. アップグレードと互換性

手数料方針の変更はコンセンサスに影響します。リリースには次を含める必要があります。

1. 新しい方針とスキーマのバージョン。
2. 有効化の高さとガバナンスの承認。
3. 旧クライアントへの応答と取引拒否の動作。
4. 決定的な移行とロールバック移行。
5. ウォレットの手数料プレビューとの互換性。
6. Indexer、Explorer、SDK、取引所、カストディの更新。
7. 監視の閾値と緊急停止条件。
8. 公開リリースノートと、置き換えられる方針への参照。

どの運用者や AI システムも、手数料、発行条件、財務資産の配分、リスク上限を黙って変更してはいけません。

## 15. 現在の証拠と制約

| 証拠 | 現在の結果 | 制約 |
| --- | --- | --- |
| コンセンサス移行チェック | レビュー対象ソースについて、2026-07-22 に合格 | ローカルの決定的なフィクスチャ |
| 署名付き送金の重点チェック | 2026-07-22 に合格 | 重点的なローカルテストであり、公開送金の証拠ではない |
| ABCI テストパッケージ | 2026-07-22 に固定された Hardhat 成果物を生成した後で合格 | 初回のクリーンチェックアウトでの実行は、生成成果物の欠落により失敗した |
| 動的ローカル手数料市場 | 無効なシャドー候補内でのみ実装され、ローカルテスト済み | 中央統合、ガバナンス、有効化、デプロイ、公開証拠のいずれもない |
| 固定手数料イベント台帳 | レビュー済み手数料候補上で実装され、ローカルテスト済み | 中央統合、デプロイ、公開インデックス化、独立した証拠による照合のいずれもない |
| Mainnet 手数料方針 | 未確立 | 経済、ガバナンス、セキュリティ、法務のレビューが必要 |
